## Discussion implications

- The threshold is **more than three**, including context, within the Q17 callable categories. Do not apply it indiscriminately to every signature: static functions are allowed, external contracts are exempt, and ordinary nonvirtual instance methods remain an open classification. Overload/configuration and repeated-plumbing rules are separate concerns.
- The current `Finish` and `Edit` APIs provide concrete recent examples, with explicit generated-by provenance. The parser, serializer, and TryFormat signatures have verified pre-June introduction history. Owner attribution alone still does not establish human authorship.
- A possible *new illustrative proposal*, not an existing or tested API, is a small `SettingsEditRequest` grouping `SettingsArguments`, `SettingsScope`, key/value/unset intent, and optional operation/item. Keep cancellation and directory/file dependencies explicit at the execution boundary if they serve separate lifecycle/configuration roles. Do not collapse unrelated dependencies into a general-purpose context bag merely to lower the count.
- Q18 accepts interface/override exemptions when the signature is imposed externally. Locally owned interfaces are not exempt. Constructors were outside this scan's scope; Q17 explicitly includes abstract-class constructors in the grouping requirement.

## Candidate redesigns for review

These are historical proposals, not source excerpts or implemented fixes. Q17
subsequently refined which callable kinds have a maximum of three parameters,
including context. The serializer grouping immediately below was rejected.

The serializer currently receives a schedule and its hash separately. The
following proposed grouping was rejected as unhelpful; retain it only to explain
the decision, not as a recommended rewrite:

```csharp
readonly record struct ScheduleSerializationInput(Schedule Schedule, string Hash);

// Proposed signature:
Task Serialize(ScheduleSerializationInput input, Stream outputFile,
    CancellationToken cancellationToken);
// Proposed call replacing Serialize(schedule, json, "", cancellationToken):
await ScheduleSerializer.Serialize(new(schedule, ""), json, cancellationToken);
```

The [cache loader](https://github.com/AntonC9018/ScheduleLib/blob/4c26748e448fe7ccbdffc3f8f6c4b05ffddce144/src/Features/Integration/Tasks/Initialization/ScheduleLoader.cs#L39-L88)
computes the hash from configuration and loader inputs, compares it with the
stored model's Hash, and passes it when writing the built schedule. Thus it is
cache validity metadata, not simply a hash of the schedule's serialized bytes.
FmiPdfImport passes an empty hash. Grouping these as serialization payload plus
metadata was the rejected proposal. The chosen direction is a builder that
configures the entire operation, including the output and optional hash.

For AddOrMergeLesson, a candidate is a named lesson occurrence containing the
parsed lesson, day, time slot, groups, and alternative, passed as one value. Check
existing lesson/occurrence models before adding another. The current five values
should not merely be hidden in an unstructured context bag.

For the newer CLI examples, Finish should first be checked against the existing
CliCompletion<T> rather than inventing another completion type. A cohesive edit
request is another possible improvement; cancellation and genuine execution
dependencies should remain explicit. These are design investigations, not proof
that either static method violates the revised parameter-count rule.

## Q17 builder direction

For the serializer, the user chose a reusable builder: configure Input and
Output (stream/path alternatives), optionally Hash (default empty), then call
ExecuteAsync(cancellationToken). The proposed schedule/hash record is rejected.
The builder's exact API and required-configuration checks remain implementation
and research work. Static functions may otherwise retain separate arguments;
more than three parameters require grouping in locally owned interfaces,
virtual/abstract methods, abstract-class constructors, and delegate types.
Q19 requires a builder for operations with more than one parameter and an
alternative overload form for at least one parameter. Ordinary nonvirtual
instance-method grouping remains open pending usage review. Repeated argument
plumbing requires a builder or context, with semantic review by agents.

## AddOrMergeLesson usage for Q20

All excerpts are from the pinned `4c26748` source above. The maintainer explicitly
identifies the shown import/plumbing code as AI-generated by Astra. Its
owner-attributed commit history is not evidence of human authorship or approval. Snippets below
omit unrelated parsing/setup; the linked methods retain the complete context.

### Word adapter gathers coordinates from parser state

[WordScheduleParser.cs, lines 525–541](https://github.com/AntonC9018/ScheduleLib/blob/4c26748e448fe7ccbdffc3f8f6c4b05ffddce144/src/ScheduleLib/ScheduleLib.Core/Parsing/WordScheduleParser.cs#L525-L541)
contains a private static extension adapter with the same name. It accepts
parser state, lesson, column index, and column span, gathers the groups covered
by the cell, and then calls the instance method:

```csharp
c.AddOrMergeLesson(lesson, state.CurrentDay!.Value,
    state.Time!.Value.TimeSlot, groups);
```

The earlier report linked the call to this adapter instead of its forwarding
call to the actual five-parameter instance method; the observed-shapes link is
now corrected. The adapter and instance method are distinct resolved methods.

### PDF import forwards the same values through an optional delegate

[PdfScheduleImporter.cs, lines 10–10 and 60–80](https://github.com/AntonC9018/ScheduleLib/blob/4c26748e448fe7ccbdffc3f8f6c4b05ffddce144/src/Features/ParsePdf/PdfScheduleImporter.cs#L60-L80)
defines ImportedLessonHandler with five parameters (declaration at line 10):

```csharp
public delegate void ImportedLessonHandler(ParsedLesson lesson, DayOfWeek day,
    TimeSlot slot, IReadOnlyList<GroupId> groups, string? alternative);
```

Within the import loop it resolves day/time, parses lesson text, resolves group
IDs (possibly narrowing a group by PartitionHint), and dispatches:

```csharp
if (addLesson is null)
    context.AddOrMergeLesson(lesson, day, time, groups, new(cell.Alternative));
else
    addLesson(lesson, day, time, groups, cell.Alternative);
```

Only layout is expanded here; the expressions and control flow are unchanged.
The locally owned delegate is already within the accepted contract-grouping
scope. That fact does not settle the ordinary instance-method category.

### Cohort handler adjusts groups and alternatives before forwarding

[ElectiveCohorts.cs, lines 71–104](https://github.com/AntonC9018/ScheduleLib/blob/4c26748e448fe7ccbdffc3f8f6c4b05ffddce144/src/Features/Integration/Tasks/Initialization/ElectiveCohorts.cs#L71-L104)
accepts the same values in its Add method. It forwards non-target courses with
the default alternative, uses an explicitly supplied cohort when present, or
iterates groups and their configured alternatives. Representative actual calls:

```csharp
_context.AddOrMergeLesson(lesson, day, slot, groups);
_context.AddOrMergeLesson(lesson, day, slot, groups, new(cohort));
// Inside the group/alternative loops:
_context.AddOrMergeLesson(lesson, day, slot, [group], alternative);
// Otherwise, for the group without configured alternatives:
_context.AddOrMergeLesson(lesson, day, slot, [group], BaseAlternative);
```

These calls occur in separate branches; they are not four sequential calls for
every lesson. Lesson/day/time are forwarded unchanged while groups and
alternative vary according to cohort policy.

### The callee already builds and merges

[ScheduleImportContext.cs, lines 303–387](https://github.com/AntonC9018/ScheduleLib/blob/4c26748e448fe7ccbdffc3f8f6c4b05ffddce144/src/ScheduleLib/ScheduleLib.Core/Parsing/ScheduleImportContext.cs#L303-L387)
creates a detached regular-lesson builder. It uses the lesson's explicit start
time when present, otherwise the supplied time slot; sets day, parity,
alternative, common lesson properties, and groups; then merges matching lessons
or attaches a new one. A lesson's explicit group name may override the supplied
groups. Moving this policy out to callers is not implied by grouping arguments.

[ScheduleCellParserTests.cs, lines 14–41](https://github.com/AntonC9018/ScheduleLib/blob/4c26748e448fe7ccbdffc3f8f6c4b05ffddce144/src/ScheduleLib/Tests/Parser/ScheduleCellParserTests.cs#L14-L41)
checks that repeated cells merge groups while retaining the time override, and
that different cohort alternatives do not merge. These are source assertions;
no new test run was performed for this documentation update.

**Q20 decision:** use one shared record struct containing all five values,
including the delegate and cohort adapter. Preserve the import context's merge
policy and the per-cohort changes to groups/alternative. The maintainer recalls
an analogous Excel-import pattern; the [Luna scan](excel-import-input-research.md)
confirmed AddLessonParams, a readonly ref struct, as a precedent. The final
clarification is to give PDF/Word their own record struct shared by their
delegate, cohort handler, and AddOrMergeLesson method. Excel retains its
separate type. The previous cross-format unification interpretation is
superseded. This concrete decision does not establish a blanket rule for all
nonvirtual instance methods.
